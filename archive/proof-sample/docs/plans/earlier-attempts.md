# Earlier attempts: failure to countermeasure

Status: Phase 0 input accepted from the repository owner; countermeasures remain subject to implementation evidence.

This record captures the concrete failure modes raised during architecture review. It does not claim organizational causes that were not reported.

| Earlier failure or dead end | Countermeasure in this repository | Proof before broader adoption |
| --- | --- | --- |
| One aggregate reacting to another aggregate's domain event had no clear ownership and encouraged hidden cascades. | A same-module application use case explicitly coordinates aggregate changes. Separate-commit reactions use a named durable process. No recursive aggregate-changing dispatch from `SaveChanges` or `ChangeTracker`. | Tests show the complete local transaction or durable transition, including rollback, duplicate delivery, and compensation. |
| Event-sourced decider/hydration behavior was not fully solved. | Limit event sourcing to Inventory Stock Position. Historical and newly decided events use one deterministic evolution function; only newly decided events become uncommitted. Expected-version append and inline projection are explicit. | Evolution fixtures, latest/version/as-of hydration, optimistic conflict, replay-without-side-effects, and inline-projection rollback tests pass. |
| The relationship between ordinary domain events and event-source events was unclear. | State-stored and event-sourced aggregates use separate bases with a small pending-event concept only where useful. A state-stored domain event is transient unless explicitly mapped; a Stock Position event-source event is durable state. Integration events remain separate contracts. | Persistence tests prove exactly which events are stored, which are dispatched, and that replayed events are never re-emitted. |
| Event-driven communication did not have a complete acknowledgement, retry, idempotency, or atomicity story. | Use RabbitMQ/Rebus for real delivery behavior, module-owned transactional outbox/inbox records, semantic business-operation IDs, isolated module endpoints, bounded technical retries, named error queues, and module-owned process state. | Failure tests kill the process before commit, after commit/before acknowledgement, during outbox dispatch, and on poison messages; resulting business state remains correct. |
| Adding a new event consumer did not answer how that consumer obtains current state. | A new consumer uses an owner-produced versioned snapshot plus high watermark, then consumes the integration-event tail and reconciles. It never replays another module's private domain/event-source history. | The Purchasing Stock Item reference consumer starts after existing Inventory data, catches concurrent updates without gaps, restarts idempotently, and reconciles to the owner. |
| Durable saga/process state and its transaction with module data were not clear. | The first Order Fulfilment Process is a concrete Sales model stored through `SalesDbContext`. Inbox, process transition, Sales changes, deadlines, audit, and outgoing outbox rows share one explicit transaction. No generic saga base or Rebus saga persistence in v1. | Concurrent and duplicate outcomes, restart, deadline claim, compensation, and ambiguous-delivery cases pass against PostgreSQL and RabbitMQ. |
| A `DbContext.SaveChanges`/`ChangeTracker` override was used to recursively create and react to events, making transaction and recursion behavior hard to reason about. | Persistence may validate tenant identity and deterministically update explicitly selected inline data, but it does not discover workflows. Handlers decide aggregates, audit, outbox messages, and transaction scope visibly. | Architecture tests reject forbidden dispatch dependencies; integration tests show multiple saves are atomic only under the handler's explicit transaction. |
| TypeScript Aspire hosting had unreliable start/stop maintenance behavior. | Use a conventional C# AppHost project and resource lifecycle commands, with `DistributedApplicationTestingBuilder` coverage. The Migrator is finite and the application waits for its completion. | Repeated start/stop tests leave no orphaned resources, migration failure prevents app startup, and CI can start the same topology. |
| “Easy extraction” risked hiding synchronous calls behind a fake local/remote abstraction. | Keep immediate in-process Contracts honest. Stable integration contracts, module queues, inbox/outbox, snapshot bootstrap, and a cutover playbook support extraction, but synchronous dependencies must be redesigned deliberately before a move. | A cutover test transfers one module endpoint queue to a separate worker and verifies state bootstrap; it does not claim zero-work extraction. |
| Reusable infrastructure and framework ideas could grow before the reference product proved them. | Implement concrete vertical slices first. Extract a focused shared mechanism only after two real consumers show the same need; copy/rename remains the default product-scaffolding path. | A second concrete use demonstrates repeated code and a deletion test shows the extracted module removes meaningful complexity from callers. |

## Working rule

Before v1, implementation evidence may invalidate any countermeasure. When that happens, stop, revise the plan and ADR status, and rebuild the affected area cleanly. Do not preserve a failed pre-v1 design through compatibility layers merely because it already exists.
