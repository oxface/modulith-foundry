# Broker and projection operations

This is an operational evidence record for 5.6b/c, not a generic replay framework or an exactly-once claim. The owner accepted local-phase closure on 2026-10-02. The [closure checklist](durability-closure-checklist.md) retains unproven windows and the pre-deployment bounded-publication/shutdown gate.

## Broker-owned observations

Inspect each module's input and named `.error` queue through RabbitMQ's platform monitoring, independently of API liveness. Ready messages await a consumer; unacknowledged messages belong to an unsettled delivery. A zero ready count does not establish completion: a receiver can commit while the delivery remains unacknowledged. Queue statistics are sampled and may lag.

The [native management API](https://www.rabbitmq.com/docs/http-api-reference) provides `messages_ready` and `messages_unacknowledged`. [RabbitMQ recommends Prometheus for production monitoring](https://www.rabbitmq.com/docs/management); use an external platform collector rather than another API-hosted broker-monitor worker. Keep management access private, use TLS and least-privilege monitoring credentials, and do not put credentials or message bodies in telemetry. The test-only management probe uses the disposable broker's existing credentials; it is not a production credential policy.

Watch ready depth, unacknowledged deliveries, consumer availability, error-queue growth and broker resource alarms alongside module outbox/process age and freshness observations. These queue counts do not provide a broker oldest-message-age measurement. Publisher confirmation establishes broker acceptance, not subscriber existence or business completion. Never purge a queue or fabricate a new OperationId to make a dashboard green.

## Explicit recovery

1. Identify the owning process and original operation/message identities from controlled evidence. Expired application deadlines do not prove that a remote effect failed.
2. Diagnose the receiver, storage, binding or schema fault before attempting recovery. Preserve error-queue evidence privately; do not paste full envelopes into logs or tickets.
3. For destination redrive, retain the original body, logical type and MessageId, producer, causation, correlation and tenant metadata. Select the owning module's original destination. Do not convert a failed command into a fabricated success outcome. Repeated redrive is explicit operator action, not an automatic poison loop.
4. Reading a broker message is not passive inspection: the management message-get API can settle or requeue deliveries and alter ordering. Use read-only queue statistics first. Any payload capture/removal/redrive requires a controlled procedure that retains evidence until receiver recovery is verified. The disposable test observer is not a shipped operator tool.
5. Source republication is a different operation. Inventory's [retained-outcome recovery Contract](message-delivery-recovery.md) preserves the stored outgoing identity and checks authorization, observed attempts and leases. Replaying an already processed command does not automatically republish its old outcome.
6. Verify business state through the owning Contracts, not broker counts alone: retained operation identity, one stock/history or requirement/activity effect, and the process's actual transition. Check both source and receiver. Dispose a failed DI scope before retrying a storage operation.

Existing trusted module recovery/reconciliation Contracts and native broker tools remain the available seams. No arbitrary-payload HTTP endpoint or generic maintenance adapter is added. Their existence is not a standalone operator UI/CLI or permission to construct a trusted Organization context from caller-supplied IDs.

## Projection failure signals

Purchasing publishes `stock_item_projection.processing_failures` for failed typed reference-adapter attempts and `stock_item_projection.reconciliation_failures` for failed explicit inspection/repair attempts, under the `modulith_foundry.purchasing` prefix. Failures before the typed adapter enters, such as deserialization or missing-handler activation, remain transport/error-queue observations rather than this counter. Requested cancellation is excluded. Retries count again; these are process-local technical attempt counters, not durable rejected-business-event counts. Neither initial Ready nor an empty error queue proves tail completeness.

Inventory publishes `modulith_foundry.inventory.stock_position_projection.rebuild_failures` for unexpected explicit rebuild failures. Normal missing/denied results and requested cancellation are not failures. A failed rebuild preserves the prior persisted projection; an operator must diagnose and explicitly retry. It does not mutate event history or replay audits/messages.

Safe module diagnostics include only stable IDs and exception type, not exception text, SQL, tokens or full payloads. Transport/framework logging has its own configuration and must also follow deployment redaction policy; these module logs do not sanitize every external library's output.

Inventory explicitly registers the native meter factory so administrative rebuilds can be composed without Rebus. [Microsoft.Extensions.Diagnostics 10.0.12](https://www.nuget.org/packages/Microsoft.Extensions.Diagnostics/10.0.12) supplies this registration and uses the MIT license (verified from the installed package manifest); its version matches the existing Microsoft runtime package baseline. [Microsoft's instrumentation guidance](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/metrics-instrumentation#best-practices) recommends DI-owned meters. This is neither an Aspire dependency nor a transport requirement for persistence.

## Tested evidence and extraction findings

- [BrokerOperationalTests](../../tests/BrokerTests/BrokerOperationalTests.cs) distinguish a retained ready delivery with an offline receiver from a committed but unacknowledged delivery, then prove failover without a second stock effect. A sender cannot create its missing destination: the receiver must first declare its durable queue. The error case observes the named error queue before consuming it, repairs storage, and explicitly redrives the original command through the real broker.
- [FirstDeliveryRaceTests](../../tests/BrokerTests/FirstDeliveryRaceTests.cs) pause actual receipt reads in two independent Inventory processes before either first delivery commits. Both identical MessageId and new MessageId/same OperationId races result in one reservation and stream advance. Sales uses the same barrier at its own first receipt read and completes compensation once; Purchasing uses its existing checkpoint row lock with a held first transaction and creates one retained requirement. This is distinct from redelivery after an already committed receipt, and the Purchasing lock must not become an assumed generic inbox guarantee. After NACK, delivery may move to either receiver: all six corrected cases require every physical delivery to complete and input/error-queue settlement, not sticky consumer ownership. The full run rejected the original same-receiver retry assumption.
- [ReceiverShutdownTests](../../tests/BrokerTests/ReceiverShutdownTests.cs) request the real Generic Host shutdown while a delivery is held after commit/before ACK. The owned receiver exits successfully within the test's 20-second bound; a replacement settles the original identity without a repeated effect. The private stdin channel is test coordination, not a production management endpoint or a proof of every operating system signal path.
- [RebuildOperationalTests](../../tests/BrokerTests/RebuildOperationalTests.cs) reject a real projection update, observe its failure counter and unchanged persisted state/version, then prove explicit repair from retained events. [StockItemProjectionRecoveryTests](../../tests/BrokerTests/StockItemProjectionRecoveryTests.cs) cover ongoing reference processing/error redrive and failed reconciliation checkpoint rollback with the new counters.
- The full [authenticated API workflow](../../tests/TopologyTests/LocalRuntimeTests.SalesOrderApproval.cs) runs with one and two complete API replicas. Both real processes run shared hosted workers; one replica is stopped and the same BFF session continues through shortage/replenishment and cancellation on the survivor. This same-VM proof is not multi-node Data Protection key-ring evidence. A reachable disposable OTLP receiver is used: default exporter-target availability affected shutdown timing during diagnosis, so this test does not establish graceful timing during a telemetry-backend outage.
- [WorkflowOperationalTests](../../tests/BrokerTests/WorkflowOperationalTests.cs) stop and restart the retained PostgreSQL container without restarting the application, preserve pending process identity, observe stale-but-not-empty diagnostics, and complete one reservation after infrastructure recovery. This is controlled stop/start, not a storage-loss, network-partition or disaster-recovery proof.
- The authenticated workflow also terminates both owned API processes around cancellation commit and restarts them through native Aspire commands. A test-only trigger holds the pre-commit write; PostgreSQL's transactional NOTIFY coordinates post-commit death. The caller deliberately discards any HTTP result, inspects retained state after restart, and retries the original cancellation. It proves rollback versus retained commit and compensation recovery, not death before response bytes were emitted. The test asserts a single release history entry and an unchanged cancellation timestamp on repeated requests. No production fault endpoint, fake handler or SQL business-state assertion is introduced.
- [InventoryCrashRecoveryTests](../../tests/BrokerTests/InventoryCrashRecoveryTests.cs) now start the competing publisher while the first publisher is still alive at post-publication/pre-mark. After the first dies, the already-running survivor waits for the real production 30-second lease and republishes the exact original outcome. Stock/version remain unchanged. An expired lease still does not prove that a slow publisher is dead; token fencing and receiver idempotency remain necessary.
- [ReplicaPoisonTests](../../tests/BrokerTests/ReplicaPoisonTests.cs) arrange one poisoned physical delivery with two live receivers, observe named error-queue quarantine, count actual failed handler attempts per process, repair the cause and explicitly redrive the original intent. The test requires at most three failed attempts per unchanged process and three to six in total for this single-copy scenario. This is not a global cap across repeated publication, restarts or changing replica sets; it is separate from successful deduplication.

All cases stay in the existing Broker or Topology CI lanes. Their time bounds cover the arranged faults, not every deployment's termination grace period or all message types. Rebus's local three-attempt retry tracker is not a distributed/global poison cap. The pinned [Rebus RabbitMQ configuration](https://github.com/rebus-org/Rebus.RabbitMq/blob/10.1.1/Rebus.RabbitMq/Config/RabbitMqOptionsBuilder.cs) selects a 60-second value for our explicit `SetPublisherConfirms(true)`, but the [10.1.1 transport](https://github.com/rebus-org/Rebus.RabbitMq/blob/10.1.1/Rebus.RabbitMq/RabbitMq/RabbitMqTransport.cs) only stores it: `BasicPublishAsync` receives neither that timeout nor an application cancellation token. Setting a shorter option alone therefore does not prove bounded publication, connection acquisition, internal retries or whole-host shutdown. This confirms the [earlier transport research](../research/2026-10-01-inventory-messaging.md). Confirmation stalls and unavailable telemetry-exporter shutdown are accepted local-phase limits, not deployment acceptance; a separate bounded-stall proof remains required before Slice 7. No transport setting has been changed here.

Mechanics worth extracting later include scoped instrumentation, receipt/semantic deduplication, transaction rollback, broker settlement and identity-preserving delivery. Module choices remain the message set, fingerprints, permissions, process transitions and projection interpretation. No new shared reliability library or generalized repair pipeline is introduced by these proofs.
