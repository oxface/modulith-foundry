# Stock Item snapshot and RabbitMQ tail

Research date: 2026-10-01. Proposed protocol and its limits; not an accepted architecture decision. Repository baseline: Rebus 8.9.5, Rebus.RabbitMq 10.1.1, Rebus.ServiceProvider 10.7.2, Npgsql 10.0.3 ([central versions](../../Directory.Packages.props)).

## A committed-prefix cursor

A PostgreSQL sequence is an allocation order, not a commit order. `nextval` is concurrent and nontransactional: A can allocate 10, B allocate 11 and commit, then A commit. A snapshot watermark of 11 would incorrectly discard A's later event. Aborted allocations also remain consumed. [PostgreSQL sequence semantics](https://www.postgresql.org/docs/18/functions-sequence.html).

Proposed inference from PostgreSQL's transaction and locking guarantees: every Stock Item writer updates one pre-created Inventory-owned counter row with `UPDATE ... SET value = value + 1 RETURNING value`, then writes the item's cursor, current state and outbox event in that same transaction. `UPDATE` holds a conflicting row lock until transaction end; the next writer cannot allocate until its predecessor commits or aborts. Rollback rolls back the counter too. Consequently visible committed cursor H denotes a completed prefix. Every relevant mutation must participate, with consistent lock acquisition order; do not release this lock via a savepoint rollback and then retain its allocation. This serializes these writers, not broker publishing. [PostgreSQL row locking](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS).

Export through the Inventory contract in one read-only `REPEATABLE READ` transaction: read the counter first as H using an ordinary `SELECT`, then materialize all Stock Items in the same transaction, and return rows plus H after success. PostgreSQL fixes this snapshot at the first non-control statement and reuses it across queries, including phantom protection. Thus the rows and H describe the same committed prefix even if a writer commits during export. `READ COMMITTED` queries do not share that guarantee. Separate transactions for H and rows invalidate the argument. [PostgreSQL isolation](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ).

## Bind before taking the snapshot

1. Establish a stable consumer-owned durable queue, nonexclusive and without auto-delete, with durable exchanges and matching Stock Item topic bindings. Await subscription completion before invoking export. Rebus.RabbitMq 10.1.1 uses centralized subscriptions and awaits `QueueBindAsync` in `RegisterSubscriber`; queue declaration uses configured durability settings. Re-declare and subscribe on process startup. [Tagged transport implementation](https://github.com/rebus-org/Rebus.RabbitMq/blob/10.1.1/Rebus.RabbitMq/RabbitMq/RabbitMqTransport.cs).
2. Keep handlers paused while materializing and installing the snapshot. Rebus supports zero workers and subsequently increasing them; all replicas sharing this queue need the same bootstrap gate. Alternatively, receive into a durable consumer-owned buffer. Never acknowledge and discard updates during initialization. [Rebus workers](https://github.com/rebus-org/Rebus/wiki/Workers-and-parallelism).
3. Install the complete snapshot and durable bootstrap watermark H atomically in the consumer database, then enable handlers. Discard events with cursor <= H because their effects are represented. For > H, apply full-state events only when their per-item cursor exceeds that item's stored cursor; persist inbox/deduplication and projection changes together before successful handler return. This application protocol tolerates duplicate and reordered state events. Deactivation must be included; a future physical deletion requires an explicit deletion fact/tombstone.

The gap-free argument is conditional: commits represented by H are covered by the snapshot; all later commits have a transactional outbox event and occur after the binding barrier. A reliable confirmed outbox relay eventually routes them to that retained queue. Publisher confirmation alone does not establish routing: even an unroutable publish can be confirmed. Preserve durable messages, confirms, queue storage and bindings; prevent TTL, overflow eviction and queue expiry from silently dropping the tail. [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [RabbitMQ durability](https://www.rabbitmq.com/docs/queues#durability).

A viable sample-local alternative to paused handlers is a durable coalesced buffer: the consumer's full-state per-item rows accept only newer source revisions while bootstrap is incomplete, but queries expose them only after a durable Ready flag. Snapshot installation merges rows by that same revision rule and marks Ready in a short transaction, serialized with handlers through one consumer-owned bootstrap-row lock. Thus a newer event received during export survives an older snapshot row, and an older late event cannot overwrite the snapshot. This is an application design inference, not built-in Rebus behavior or tested evidence. It works for complete current-state events and the producer's no-deletion lifecycle; deletion or collection-wide replacement needs tombstones/reconciliation. The tradeoff is serialization at the consumer gate rather than retaining an event history, with simple restart by repeating the export until Ready.

## Ordering, restart and practical limits

RabbitMQ order follows publishing channels, not database commit order; multiple publishers interleave, and consumers/redelivery can reorder effective handling. Do not advance a global discard watermark to the largest delivered cursor: receiving 12 before 11 must not suppress 11 for another item. H is a snapshot boundary; per-item versions protect subsequent full-state upserts. Delta events require additional ordered buffering/replay. [RabbitMQ ordering](https://www.rabbitmq.com/docs/queues#message-ordering).

After installation, restart with the persisted consumer state and the same queue. Crash before installation restarts export behind the gate; crash after a consumer database commit but before ACK can redeliver, so the handler must be idempotent. Error-queued poison messages require repair and replay; they do not constitute a completed tail. Losing the queue or projection requires a fresh bootstrap, with the binding established again first. [RabbitMQ reliability](https://www.rabbitmq.com/docs/reliability), [Rebus retry implementation](https://github.com/rebus-org/Rebus/blob/8.9.5/Rebus/Retry/Simple/DefaultRetryStep.cs).

This proposal targets the sample's small catalog: the singleton counter is a write bottleneck, and the export fully materializes data while holding a database snapshot. Paginated exports across independent transactions would need a different consistency protocol. It supplies current state plus future delivery, not historical events or a cursor-based replay API; a standard queue cannot retrospectively deliver messages published before it was bound. Broker loss and permanent relay/consumer failure remain operational recovery concerns, not guarantees erased by the cursor.
